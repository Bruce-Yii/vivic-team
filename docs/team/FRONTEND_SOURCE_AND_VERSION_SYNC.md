# 前端源码留存与协作仓库版本同步规范

> 原始基准仓库：`Bruce-Yii/vivic-team`。
> **后续实际协作仓库：由协作者将原始仓库复刻到自己账号下形成的仓库。** 仓库所有者、完整名称和默认分支在启动协作前登记。
> 本文件放在原始仓库中，供复刻后的仓库继承；它不表示后续开发仍在 `Bruce-Yii/vivic-team` 中进行。

## 1. 先确定在哪里协作

### 1.1 两个仓库，两个职责

| 仓库 | 职责 | 是否作为后续协作目标 |
| --- | --- | --- |
| `Bruce-Yii/vivic-team` | 原始产品源码、历史基线和复刻来源 | 否，默认只读参考 |
| 协作者账号下复刻的仓库 | 实际开发、任务管理、代码提交、评审和集成 | **是，唯一协作目标** |

后续 ChatGPT、用户、本地 Agent 和其他协作者，必须围绕同一个协作者仓库工作。不能有人在原始仓库开发、有人在复刻仓库开发，再试图靠口头同步版本。

**默认禁止：**

- 不在原始仓库创建后续开发 Issue、任务分支或 PR；
- 不把 PR 的 base 指向 `Bruce-Yii/vivic-team:main`；
- 不把原始仓库的临时运行状态、单次检查结果或本窗口的诊断记录当成协作者仓库的验收证据；
- 不擅自把原始仓库的自动化工作流、分支保护、密钥或运行配置作为新协作环境的既定配置。本规范不要求迁移或修改这些内容。

### 1.2 复刻完成后的启动登记

开始任何开发前，先确认并记录：

- 协作者仓库完整名称：`<COLLABORATOR_OWNER>/<COLLABORATOR_REPO>`；
- 默认分支：通常为 `main`，以 GitHub 仓库设置为准；
- 仓库所有者已授予实际协作者写入或 PR 所需权限；
- 所有参与者都能访问同一个协作者仓库；
- 原始仓库与协作者仓库的关系：GitHub Fork，还是独立复制。

在上述信息没有确认前，不创建任务、不推送分支、不创建 PR。

## 2. 源码与构建产物必须分清

### 2.1 唯一源码真值

Web 前端可编辑源码以协作仓库中的 `apps/web/` 为准，包括：

- `apps/web/src/`：页面、组件、状态、请求和交互实现；
- `apps/web/public/`：随应用发布的静态资源；
- `apps/web/package.json`、Vite 配置及根目录 `package.json`；
- 根目录 `pnpm-lock.yaml`：依赖版本的锁定依据；
- 必要的测试、类型、样式和构建配置。

任何准备交付、部署或让其他人继续开发的前端修改，都必须先进入可编辑源码，并通过 Git commit 留在**协作者仓库**中。

### 2.2 构建产物不是源码

以下内容属于生成结果，不是可维护的源代码：

- `dist/`；
- `assets/*.js`、压缩后的 chunk；
- 带 hash 的 CSS、JS、图片及其他静态 bundle；
- 服务器 Web 根目录中直接复制的发布文件。

禁止把线上 bundle 当作正常开发入口，禁止直接编辑压缩 JS 后声称源码已更新。Source map 也不能替代完整源码、依赖清单和构建配置。

服务器 2026-11-08 Web release 的部分内容目前只有构建产物，缺少完整可编辑源码。这是历史交接缺口，不代表这些 bundle 可以作为新的源码基线。需要复用其行为时，先对照现有 `apps/web` 源码和线上页面，明确差异；不能直接用旧源码全量构建覆盖服务器补丁。

### 2.3 每次前端交付必须留下什么

一个前端任务至少留下：

1. 可编辑源码及必要静态资源；
2. 对应测试或明确的人工验收步骤；
3. 依赖与锁文件变化（没有变化就不改锁文件）；
4. 构建命令和实际结果；
5. 任务分支、PR 和对应 commit SHA；
6. 如果部署，另留发布记录，标明实际部署的构建产物来自哪个 SHA。

构建产物可以作为发布包或服务器部署资产保存，不要求把每次生成的 bundle 反复提交到源码目录。关键是必须能够从记录的源码 SHA 和锁文件重建它。

## 3. Git remote 与分支：始终以协作者仓库为中心

### 3.1 推荐 remote 关系

所有参与者都 clone **协作者的仓库**，而不是各自 clone 原始仓库。

若协作者仓库是 GitHub Fork：

- `origin` 指向协作者账号下的仓库；
- 可选的 `upstream` 指向原始仓库 `Bruce-Yii/vivic-team`，仅用于查看和比较来源更新；
- 日常 push、Issue、PR 和合并全部发生在协作者仓库；
- 即使仓库页面默认建议向父仓库提 PR，也必须确认 PR 的 base 是协作者仓库自己的默认分支。

若协作者仓库是独立复制：

- `origin` 指向协作者仓库；
- 不需要配置原始仓库 remote；
- 如确有溯源需要，可把原始仓库配置为只读的 `source` remote；
- 不把原始仓库当作日常 pull、push 或 PR 目标。

开始操作先检查：

```bash
git status --short --branch
git remote -v
git fetch --all --prune
git branch --show-current
git rev-parse HEAD
```

确认 `origin` 是协作者仓库后，再同步其默认分支：

```bash
git switch main
git pull --ff-only origin main
git rev-parse HEAD
git switch -c task/<issue>-<scope>
```

如果协作者仓库默认分支不是 `main`，使用仓库实际配置的分支名，不要自行创建第二条主线。

### 3.2 不要把原始仓库更新自动灌入协作仓库

原始仓库后续可能继续变化，但协作仓库是本轮工作的事实基线。需要从原始仓库取回更新时：

1. 先比较双方 commit 和文件差异；
2. 明确哪些提交或文件确实需要同步；
3. 检查是否会带入不相关的实验、工作流、配置或其他窗口产物；
4. 只同步经确认的提交或改动；
5. 在协作者仓库内重新验证。

**禁止直接把原始仓库的 `main` 无条件 merge/pull 到协作者仓库。** 不能因为原始仓库有新提交，就假定它适合当前协作分支。

### 3.3 开发中的同步方式

Git 不会自动把一个人的本地修改同步给其他人：

- 只在本地修改：别人看不到；
- commit 但没有 push：其他设备和 Agent 仍看不到；
- push 到协作者仓库的任务分支：有权限的人可以 fetch 并继续；
- PR 合入协作者仓库的默认分支：团队才有共同的新基线。

需要跨设备继续同一任务时，先 commit 并 push；另一台设备 fetch 后切到同一任务分支继续。不同 Agent 不得在同一个工作目录里同时切分支或覆盖同一批文件。

每个独立任务使用独立分支和 PR。PR 合入后，下一项任务从协作者仓库更新后的默认分支新建分支，不继续复用旧基线。

开发期间若协作者仓库的默认分支已前进：

1. 先保存当前任务改动；
2. fetch 协作者仓库的 `origin`；
3. 将协作者仓库最新默认分支同步到任务分支；
4. 解决冲突时保留双方意图，不用整文件覆盖；
5. 重新运行受影响的检查，再 push 更新 PR。

如果本地有未提交改动，先确认归属并妥善提交或分离，再切换分支；禁止用 `reset --hard`、`clean -fdx` 或整目录覆盖来“同步”。

## 4. 多人和多 Agent 的并行边界

- 所有人围绕同一个协作者仓库，但每个 Agent 使用独立 worktree / 工作目录和独立任务分支。
- 不允许多个 Agent 在同一工作目录中同时 checkout、切分支或修改同一文件。
- 有文件重叠的任务必须先确定负责人和接口，不以“并行”名义同时改同一实现。
- 需要共享中间成果时，先 commit、push 到协作者仓库的任务分支，再让下游 fetch 指定 SHA；不能依赖本机未提交文件或口头描述。
- 任务交接必须给出仓库名、分支、基线 SHA、当前 HEAD SHA、已提交/未提交状态和剩余事项。
- PR 的 base 和 head 都必须属于协作者仓库；除非用户明确要求，否则不向原始仓库提 PR。

## 5. 前后端接口必须按同一份契约协作

- `packages/contracts/` 是共享 API / 数据契约的维护入口；生成文件按仓库脚本更新，不能手工制造前后端两套定义。
- 后端新增字段或接口时，先定义类型、必填性、默认值、错误形状和兼容策略，再分别实现后端与前端。
- 优先采用向后兼容的增量变更：先让后端同时兼容旧、新调用，再更新前端；确认旧调用退出后，才考虑移除旧字段。
- 破坏性变更必须拆成迁移步骤，不能在同一个发布动作里让旧前端突然调用新后端，或让新前端依赖尚未部署的后端字段。
- Mock、fixture 和 Demo 数据必须标明；不能用 Mock 结果证明真实 API 已经可用。

后端任务如果没有修改 API 契约，不应要求前端跟着重构或重新发布。

## 6. 前后端开发范围

当前优先推进后端协作。前端近期改动较少，因此：

- 后端任务默认不改 Web 页面、不重打前端包，也不顺手升级前端依赖；
- 只有任务明确涉及页面、浏览器行为或前后端接口时，才修改对应前端文件；
- 后端改动影响 API 契约时，必须先说明兼容策略，不能让前端、后端各自猜字段；
- 本规范不授权部署、重启服务器、修改生产配置或覆盖线上文件。

## 7. 前端发布与服务器版本记录

发布必须遵循“从一个确定的源码 SHA 构建一次，再部署这一份产物”，不能在服务器上临时改源码、临时拼 bundle，最后无法追溯。

每次正式发布，在协作者仓库的 `docs/operations/releases/` 下新增一份简短记录（目录不存在时再创建），至少包含：

| 字段 | 记录内容 |
| --- | --- |
| Release 时间 | 实际部署时间与时区 |
| Frontend source | 前端源码 commit SHA |
| Frontend artifact | 构建包名称及 SHA-256 |
| Backend source | 后端 commit SHA / 部署版本 |
| Contract | 使用的契约版本或对应 commit SHA |
| Build | Node、pnpm 版本及实际构建命令 |
| Validation | 实际执行的检查命令、结果和环境 |
| Database | 是否涉及迁移；无迁移写明无 |
| Rollback | 上一个可恢复的前端/后端版本 |

发布前后都要记录服务器实际运行版本。不能只记录“已更新”或某个可变分支名。

如果发现服务器有仓库里没有的前端补丁：

1. 先备份并核对线上实际文件，不覆盖；
2. 确认差异属于哪个页面、资源和行为；
3. 尽可能恢复为可编辑源码，补入协作者仓库并经 PR 审查；
4. 若无法恢复，明确标注为不可重建的历史补丁，保留其发布包和 hash；
5. 在源码补齐前，不得用旧源码构建产物覆盖它。

## 8. 任务验收清单

### 前端任务

- [ ] 开发发生在协作者仓库，而不是原始仓库。
- [ ] 修改落在 `apps/web` 的可编辑源码中，不是只改服务器 bundle。
- [ ] 任务分支来自协作者仓库已记录的最新默认分支 SHA。
- [ ] API 调用与 `packages/contracts` 对齐。
- [ ] 运行受影响的前端测试、类型检查和构建，并记录真实结果。
- [ ] PR 的 base 是协作者仓库自己的默认分支。
- [ ] 若发布，发布记录能追溯到源码 SHA 和构建产物 hash。

### 后端任务

- [ ] 开发发生在协作者仓库。
- [ ] 明确本次是否影响前端/API 契约。
- [ ] 未涉及前端时，不改前端文件、不重打前端包。
- [ ] 涉及契约时，先更新共享契约并提供兼容策略。
- [ ] 后端测试与集成验证对应当前任务 SHA。
- [ ] 不用前端旧 bundle、Mock 页面或静态截图冒充后端真实验收。

## 9. 给 Agent 的固定开工指令

```text
先确认本轮实际协作仓库的 owner/name、默认分支和访问权限。原始仓库 Bruce-Yii/vivic-team 只是源码来源，不是本轮默认开发目标。
所有 Issue、分支、commit、PR 和集成都发生在协作者仓库。开工前核对 origin、工作区状态、默认分支和基线 SHA。
本任务以协作者仓库中的 Git 源码为准，不从服务器 dist/assets 反向开发；不得覆盖线上文件或擅自部署。
当前优先后端。只有任务明确要求时才改前端；涉及 API 时先对齐 packages/contracts，并写清向后兼容策略。
开发中通过 commit/push/PR 同步，不假设其他设备或 Agent 能看到本地未推送改动。
不要自动 merge 原始仓库的 main；如需同步来源更新，先比较差异并明确批准范围。
结束时报告协作仓库名、分支、基线 SHA、HEAD SHA、PR、实际验证结果、未验证项及需要集成的接口。
```
